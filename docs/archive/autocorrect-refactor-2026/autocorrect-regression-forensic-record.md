# Autocorrect regression forensic record

> Status: Canonical forensic record
> Recorded: 2026-07-12
> Scope: Phase 2 baseline `2dc236c8`, six-commit architecture cleanup through
> `55cd2cbf`, and the subsequent on-device regression report
> Runtime behavior: unchanged by this document

This record preserves a completed source-and-repository investigation. It is
not a claim that the live failure was reproduced under instrumentation. Every
material claim is tagged with its evidence class so source facts, device
observations, reconstructions, and hypotheses remain distinct.

Evidence labels used below:

- **Confirmed from source** — established from the implementation at the named revision.
- **Confirmed from repository data** — established from Git objects, refs, diffs, assets, or GitHub metadata.
- **Observed directly by the user on-device** — reported from the installed keyboard, not generated by the replay.
- **Reconstructed by the offline diagnostic replay** — produced by a Python reimplementation under stated assumptions.
- **Agent inference** — a reasoned interpretation of confirmed facts.
- **Plausible but unproven** — a concrete hypothesis that still needs runtime evidence.
- **Unresolved** — evidence is insufficient to decide.

## 1. Executive summary

**Confirmed from repository data:** PR #50 established the successful Phase 2
feature baseline at `2dc236c8d2bc6a38978118abfdf1a0c6a77eefbb`; it merged to
`main` as `a0ffdff2f70e0144a88a5e95b226911c915e9a52`. The six cleanup
commits were then added only on `dev`, ending at
`55cd2cbff4ec126125359637c20f567b3ce9c4fa`. They were not merged into
`main` at handover.

**Observed directly by the user on-device:** The PR #50/Phase 2 work felt
substantially better in daily use. On the later `0.5.0-debug+55cd2cbf` build,
the user instead saw missed corrections, implausible apostrophe candidates,
weaker joined-word repair, and an overall feeling that autocorrect had become
globally timid.

**Confirmed from source:** Four pre-existing mechanisms explain the individual
examples without requiring a new word-specific defect in the cleanup:

1. `CommitPolicy` treats *any* changed token containing a digit as
   `NUMERIC_TOKEN`. That safely protects `742`, `PS2`, `v2`, and `3.14`, but it
   also blocks word-shaped one-key substitutions such as `sugg3stions`,
   `correc5ed`, and `5his` after retrieval has found the intended word.
2. `CandidateScorer` grants large generic apostrophe bonuses based on letter
   similarity and frequency. It does not require `ContractionRules` to license
   the candidate. This lets dictionary entries such as `La's` and `L's`
   outrank the ordinary edit candidate `last` for `las`.
3. “Valid Word Immunity” is a binary decision derived from the broad runtime
   dictionary. Because `las` is a dictionary entry, all non-casing replacements
   are vetoed regardless of the entry's provenance or trust.
4. `WordSegmentation` only accepts a split when both unchanged halves are
   already dictionary words and exactly one split has bigram evidence. It can
   repair `inthe` to `in the`; it is not designed to repair a missing boundary
   plus a typo inside one half, such as `thatbsuggestiins`.

**Confirmed from source:** `edc161d8` made one genuine behavior change inside
the six-commit series: the fallback path began calling the full `CommitPolicy`.
Before that commit, fallback autocorrection eligibility was essentially the
legacy uppercase guard (`upperCount < 2`). Afterward, fallback inherited the
digit veto, binary valid-word immunity, protected-vocabulary veto, and
anti-correction veto from coarse fallback inputs.

**Reconstructed by the offline diagnostic replay:** Under the normal primary
`NgramSuggestionEngine` assumption, no previous lexical word, no neural
verdict, and fallback not entered, baseline `2dc236c8` and HEAD `55cd2cbf`
produced equal results for all requested probes: `las`, `sugg3stions`,
`correc5ed`, `5his`, `thatbsuggestiins`, `inthe`, `teh`, `742`, `PS2`, `v2`,
`3.14`, and `zsh`.

**Plausible but unproven:** The blank keyboard/settings hang during APK
replacement, followed by successful operation after restart, makes engine
initialization failure and fallback activation a strong explanation for why the
cleanup build could feel globally more conservative even though the primary
replay was unchanged. No device log or engine-mode trace was captured, so this
must not be stated as the cause.

## 2. Project and pipeline context

**Confirmed from source:** OmniBoard's live autocorrect path is distributed
across `LatinLanguageProvider`, `SymSpellManager`/`DictionaryRepository`,
`NgramSuggestionEngine`, the shared evidence and policy components, and editor
commit handling. The intended responsibility boundaries are:

| Responsibility | Repository role | Current behavior at `55cd2cbf` | Evidence |
|---|---|---|---|
| Retrieval | `SymSpellManager` and `DictionaryRepository` | Produces edit-distance candidates and prefix candidates. | **Confirmed from source** |
| Candidate provenance | `LatinLanguageProvider.suggest()` | Retains edit versus prefix origin through `editTerms`; edit candidates are merged before prefixes so a prefix's synthetic distance zero does not replace the true edit copy. | **Confirmed from source** |
| Ranking | `NgramSuggestionEngine.rank()` and `CandidateScorer` | Orders candidates numerically from edit cost, keyboard geometry, context, bigram evidence, apostrophe evidence, user boost, and frequency. Lower penalty becomes higher UI confidence. | **Confirmed from source** |
| Contextual evidence | `ContextualEvidence` | Supplies soft numerical grammar/bigram-conflict penalties and `id -> is/I'd` context bonuses. It does not itself authorize a commit. | **Confirmed from source** |
| Contraction rules | `ContractionRules` | Owns general shortcuts, the narrower legacy fallback shortcut set, soft-grammar candidate names, and contextual `were/we're` and `its/it's` resolution. | **Confirmed from source** |
| Protected vocabulary | `ProtectedVocabulary` plus packaged `protected_forms.txt`, assembled by `PersonalPreferences` | Represents typed forms that should not be automatically replaced. Its primary architectural role is a commit veto. | **Confirmed from source** |
| Anti-correction pairs | `PersonalPreferences` | Represents specific typed-to-candidate exclusions. The general retrieval path filters these candidates before ranking and policy also checks them defensively. | **Confirmed from source** |
| Commit authority | `CommitPolicy` | Receives already-assembled booleans and a possible neural verdict, then returns ordered veto reasons. It does not retrieve or rank. | **Confirmed from source** |
| Casing | `CasingUtils` and `SymSpellManager.applyPredictedCasing()` | Formats the selected suggestion after ranking; segmentation and the contraction fast path have their own explicit casing calls. | **Confirmed from source** |
| Segmentation | `WordSegmentation` plus `BigramTable` | Runs before general retrieval and proposes one exact two-word split only when dictionary and bigram evidence identify a unique survivor. | **Confirmed from source** |
| Primary orchestration | `LatinLanguageProvider.suggest()` with non-null `ngramEngine` | Retrieves, ranks, optionally obtains a neural decision, cases each candidate, assembles policy inputs, and inserts the typed token into UI results if absent. | **Confirmed from source** |
| Fallback orchestration | `LatinLanguageProvider.suggest()` with null `ngramEngine` | Calls legacy `SymSpellManager.suggest()`, preserves an uppercase-heavy guard, and since `edc161d8` also assembles a coarse `CommitPolicy.Input`. | **Confirmed from source** |

**Confirmed from source:** A candidate's *shape*, its *relationship to the typed
token*, and its *provenance* are not currently modeled as separate rich types.
For example, `CommitPolicy` derives numeric status directly with
`typed.any { it.isDigit() }`, while fallback simply declares every returned
candidate to be an edit-distance candidate.

**Confirmed from source:** The contraction fast path precedes segmentation,
general retrieval, neural scoring, and the general `CommitPolicy` call. It
checks protected vocabulary and the exact anti-correction pair, applies casing,
and returns an auto-commit-eligible candidate directly. Thus `CommitPolicy` is
not yet literally the single commit authority despite comments claiming it is.

## 3. Original goals of the six commits

### `826c89f3` — Lock autocorrect cleanup behavior

- **Confirmed from repository data:** The commit added only
  `AutocorrectBehaviorRegressionTest.kt` (76 lines at that revision).
- **Agent inference:** The design goal was to freeze the merged behavior before
  moving ownership: protected vocabulary versus anti-correction semantics,
  contraction behavior, `id -> is/I'd` context, and soft grammar penalties.
- **Agent inference:** The intended responsibility move was none; this was a
  characterization-test boundary for later behavior-preserving extraction.
- **Confirmed from repository data:** The commit was intended to be
  behavior-preserving and did not change production code.
- **Confirmed from source:** The tests were useful pure-unit guardrails, but
  they did not assemble real candidates or provider decision inputs.
- **Current forensic judgment — Confirmed from repository data:** Unrelated to
  the runtime regression as a behavior change.
- **Remaining risk — Agent inference:** Characterization tests can preserve the
  wrong abstraction if fixtures manually provide facts that production must
  derive.

### `928a3369` — Extract contextual ranking evidence

- **Confirmed from repository data:** Important files were
  `CandidateScorer.kt` and the new `ContextualEvidence.kt` (58 additions, 47
  deletions overall).
- **Agent inference:** The goal was to keep `CandidateScorer` as a numerical
  Judge while moving embedded soft grammar lists, bigram-conflict logic, and
  the special `id -> is/I'd` preference into one small evidence component.
- **Confirmed from source:** `ContextualEvidence.rankingPenalty()` returns only
  additive numerical bonuses or penalties; it does not impose a hard commit
  rule.
- **Agent inference:** The intended extraction was behavior-preserving: the
  same arithmetic would be called from the scorer through a clearer boundary.
- **Reconstructed by the offline diagnostic replay:** No requested primary-path
  probe changed across baseline and HEAD under neutral context.
- **Current forensic judgment — Agent inference:** The architectural direction
  is sound and is not the source of the reported digit, `las`, or segmentation
  failures.
- **Remaining risk — Confirmed from source:** The component still depends on
  global `BigramTable` state, and the tests check arithmetic rather than an
  assembled candidate set.

### `3a8d0959` — Decouple segmentation bigram evidence

- **Confirmed from repository data:** The only production diff was a small
  change in `LatinLanguageProvider.kt` (one addition, two deletions).
- **Agent inference:** The goal was to stop asking the Judge
  (`CandidateScorer.bigramScore(...).hasHit`) a yes/no availability question
  needed by segmentation.
- **Confirmed from source:** The provider now calls the underlying
  `BigramTable.hasHit(left, right)` directly when supplying
  `WordSegmentation`'s callback.
- **Agent inference:** This was intended to preserve the conservative
  segmentation algorithm exactly while clarifying ownership.
- **Reconstructed by the offline diagnostic replay:** `inthe` retained its
  unique `in the` proposal with bigram frequency 439; joined-plus-typo input
  remained unsupported.
- **Current forensic judgment — Confirmed from source:** No algorithmic
  broadening or narrowing occurred in this commit.
- **Remaining risk — Agent inference:** Provider-level tests still do not prove
  that the actual table loaded and the callback executed on device.

### `edc161d8` — Separate correction policy from ranking

- **Confirmed from repository data:** Important files were
  `SymSpellManager.kt`, `LatinLanguageProvider.kt`, `CandidateScorer.kt`, and
  `AutocorrectBehaviorRegressionTest.kt` (50 additions, 28 deletions).
- **Agent inference:** The goal was to remove protected-vocabulary and
  anti-correction culling from numerical scoring, hide exact anti-correction
  pairs before ranking, and make `CommitPolicy` the owner of autocorrect vetoes.
- **Confirmed from source:** Primary retrieval filters anti-correction pairs;
  protected vocabulary is passed as a policy input; `CandidateScorer` returns
  ordinary finite numerical scores instead of `CULLED_SCORE` for those cases.
- **Confirmed from source:** The fallback path also began calling the full
  `CommitPolicy`. This was an actual behavior change, not a pure extraction.
- **Agent inference:** Applying the same authority to fallback was
  architecturally motivated, but fallback did not possess evidence equivalent
  to the primary path and supplied coarse approximations.
- **Current forensic judgment — Confirmed from source:** This is the first bad
  commit in the six-commit series for the symptom class “fallback became
  globally more conservative.” It is not the first bad primary-path commit for
  the reported word examples.
- **Remaining risk — Unresolved:** Whether the live bad session actually
  entered this changed fallback path.

### `2a284175` — Consolidate contraction rules

- **Confirmed from repository data:** Important files were
  `SymSpellManager.kt`, `LatinLanguageProvider.kt`, `CasingUtils.kt`,
  `ContextualEvidence.kt`, the new `ContractionRules.kt`, and regression tests
  (97 additions, 126 deletions).
- **Agent inference:** The goal was to remove duplicate shortcut/context maps
  from orchestration and casing code while preserving both the primary shortcut
  behavior and the deliberately narrower legacy fallback set.
- **Confirmed from source:** `ContractionRules` now owns `SHORTCUTS`,
  `LEGACY_FALLBACK_SHORTCUTS`, `SOFT_GRAMMAR_CANDIDATES`, and contextual
  resolution.
- **Agent inference:** The intended consolidation was behavior-preserving.
- **Confirmed from source:** `La's` and `L's` in the `las` result are ordinary
  dictionary retrieval candidates. They are not generated by
  `ContractionRules`; their bonuses come from generic apostrophe scoring in
  `CandidateScorer`.
- **Current forensic judgment — Confirmed from source:** This commit did not
  cause the `las` apostrophe ranking defect.
- **Remaining risk — Confirmed from source:** The fast path still bypasses the
  general `CommitPolicy`, neural gate, and ordinary ranking path.

### `55cd2cbf` — Clarify protected vocabulary ownership

- **Confirmed from repository data:** Important files were `ROADMAP.md`,
  `protected_forms.txt`, `PersonalPreferences.kt`, the new
  `ProtectedVocabulary.kt`, regression tests, and the canonical heuristic/live
  pipeline docs (54 additions, 38 deletions).
- **Agent inference:** The goal was to distinguish built-in protection ownership
  from asset-loaded protection, eliminate duplicate source declarations, and
  document that protection is primarily a commit veto rather than rank evidence.
- **Confirmed from repository data:** The packaged protected asset lost one
  `rn` line because `rn` already exists in the built-in set; the effective
  protected set was intended to remain unchanged.
- **Confirmed from repository data:** The unified dictionary and bigram assets
  are byte-identical between `2dc236c8` and `55cd2cbf` (SHA-256 values recorded
  in the diagnostic method below).
- **Current forensic judgment — Confirmed from repository data:** There is no
  evidence that this commit introduced a noisy dictionary entry or made `las`
  protected. `las` is not in protected vocabulary.
- **Remaining risk — Unresolved:** Runtime asset initialization was not observed
  during the disturbed installation session.

## 6. Detailed findings by symptom class

### Digit-bearing word-shaped typos

**Confirmed from source:** `CommitPolicy` adds `NUMERIC_TOKEN` whenever the
candidate changes and the raw typed string contains any digit. There is no
classifier separating prose-like digit substitutions from numbers, versions,
hashes, or technical identifiers.

**Reconstructed by the offline diagnostic replay:** The intended candidates
were retrieved and ranked strongly, then vetoed:

| Typed -> candidate | Edit | Keyboard | `ln(freq)` | Final penalty | Policy result |
|---|---:|---:|---:|---:|---|
| `sugg3stions` -> `suggestions` | 1 | 2.0 | 10.558 | 1.944 | `NUMERIC_TOKEN` |
| `correc5ed` -> `corrected` | 1 | 2.0 | 10.051 | 1.995 | `NUMERIC_TOKEN` |
| `5his` -> `this` | 1 | 2.0 | 14.977 | 1.502 | `NUMERIC_TOKEN` |

**Confirmed from repository data:** The overbroad predicate entered at
`2dc236c8` (“Guard numeric tokens with regression fixtures”), immediately
before the six-commit cleanup. It was already present in the requested
baseline.

**Agent inference:** The failed word-shaped cases are primarily policy/classifier
failures, not retrieval or ranking failures.

### Apostrophe candidate ranking

**Confirmed from source:** `CandidateScorer` applies `-20.0` when removing the
candidate apostrophe exactly matches the typed letters and `-10.0` for a close,
frequent apostrophe candidate. This evidence is generic; it does not ask
`ContractionRules` whether the typed-to-candidate relationship is a licensed
contraction or morphology.

**Reconstructed by the offline diagnostic replay:** With neutral context:

```text
las
  edit 0 + spatial 0 + exact -100 + frequency -0.989
  = -100.989

La's
  edit 1 + spatial 2.5 + generic apostrophe -20 + frequency -0.730
  = -17.230

L's
  edit 1 + spatial 2.0 + generic apostrophe -10 + frequency -0.901
  = -7.901

last
  edit 1 + spatial 0.5 + frequency -1.280
  = 0.220

law
  edit 1 + spatial 1.118 + frequency -1.259
  = 0.859
```

**Reconstructed by the offline diagnostic replay:** Both apostrophe candidates
beat `last` numerically even though neither is produced or licensed by
`ContractionRules`.

**Observed directly by the user on-device:** The smartbar showed approximately
`las`, `La's`, `L's`, `last`, `law`.

**Unresolved:** The frozen replay also includes prefix candidates such as
`laser` and `lasts` in its complete merged ranking, so it does not reproduce the
visible five-item list exactly. Whether the UI filtered, reordered, or truncated
the provider's full list needs a provider/UI trace. The material ordering
finding—`La's` and `L's` ahead of `last`—is common to both.

### `las` dictionary membership and valid-word immunity

**Confirmed from repository data:** `las` is in the packaged dictionary at raw
frequency 19,829 in both baseline and HEAD assets.

**Confirmed from repository data:** `las` is not in built-in protected
vocabulary, not in `protected_forms.txt`, and not an anti-correction key in the
frozen investigated tables.

**Confirmed from source:** The provider computes `typedIsValidWord` by checking
whether the ranked output contains the raw input, case-insensitively. It then
passes that single boolean to every candidate's policy decision.

**Reconstructed by the offline diagnostic replay:** The exact dictionary match
receives the large exact-match bonus and all different non-casing candidates,
including `last`, receive `VALID_WORD_IMMUNITY` at commit time.

**Unresolved:** The precise historical source and admission provenance of the
`las` dictionary row were not established. A historical contraction/dictionary
commit around `7ed8e9e1` is relevant to apostrophe vocabulary evolution, but it
is not evidence that this exact row entered from a particular source at that
commit.

### Exact missing-space segmentation

**Confirmed from source:** Segmentation rejects tokens outside length 5–24,
tokens containing non-letters, tokens already in the dictionary, splits with a
part shorter than two letters, splits whose halves are not both dictionary
words, splits without a bigram hit, and cases with anything other than one
distinct supported split.

**Reconstructed by the offline diagnostic replay:** For `inthe`, `in the` has
two dictionary-valid halves and bigram frequency 439. `int he` fails because
`int` is not a dictionary word in the selected asset. Exactly one proposal
survives, so `in the` is accepted.

**Confirmed from repository data:** This conservative algorithm originated at
`8f0832c1`, before the numeric baseline and six cleanup commits.

**Confirmed from source:** `3a8d0959` changed only who answers the bigram-hit
question, not the segmentation conditions.

### Joined token plus typo

**Reconstructed by the offline diagnostic replay:** General edit retrieval
finds no candidate within distance two for `thatbsuggestiins`. At the meaningful
boundary `that | bsuggestiins`, the left half is valid, the right half is not,
and there is no exact bigram hit. Every split fails at least one required
condition.

**Confirmed from source:** The algorithm does not retrieve corrections for each
half after proposing a boundary. A “one boundary plus one typo in a half” repair
is separate, unimplemented feature work, not a regression in `3a8d0959`.

### Primary versus fallback behavior

**Reconstructed by the offline diagnostic replay:** Under the explicit primary
engine assumption, all requested baseline and HEAD diagnosis JSON was equal.

**Confirmed from source:** Before `edc161d8`, fallback commit eligibility was
principally `upperCount < 2`. After `edc161d8`, it is `upperCount < 2` *and* a
full `CommitPolicy` decision assembled from fallback-visible data.

**Confirmed from source:** Fallback now supplies:

- `typedIsValidWord = SymSpellManager.hasWord(currentWordRaw)`;
- `isEditDistanceCandidate = true` for every fallback result;
- live anti-correction and protected-vocabulary booleans;
- no neural verdict.

**Agent inference:** Centralizing commit authority was correct in direction,
but calling the same policy with less precise evidence changed semantics. It
can globally suppress fallback corrections even when primary ranking code is
unchanged.

**Plausible but unproven:** The installation disturbance caused `ngramEngine`
to be null or initialization to fail, selecting fallback during the bad session.
This is the strongest coherent explanation for the cleanup-correlated global
dampening, but the required runtime evidence was not captured.

### Neural-state uncertainty

**Confirmed from source:** In the primary path, a neural decision only becomes
a live `CommitPolicy` veto when `useNeuralScorer` is enabled. Shadow mode logs a
decision but does not by itself make it authoritative. Segmentation is
suggestion-only when the neural gate is live because the model was not trained
on multi-word candidates.

**Unresolved:** The bad session's neural scorer could have been disabled,
shadowing, or live. The offline replay assumed no neural verdict and therefore
cannot attribute any device rejection to neural behavior.

### Control probes

**Reconstructed by the offline diagnostic replay:** `teh -> the` ranked as an
allowed edit correction. `inthe -> in the` survived segmentation. `742`, `PS2`,
`v2`, and `3.14` remained non-destructive. `zsh` remained the exact top match.

**Confirmed from repository data:** `zsh` is a dictionary word with frequency
100,438 and is not in protected vocabulary. Its safety is due to exact-match
ranking plus valid-word immunity, not the protected-vocabulary mechanism used
by an existing test fixture.

## 8. Test-quality audit

### What the tests usefully cover

**Confirmed from source:** `CommitPolicyTest` checks each pure blocker,
evaluation order, casing exceptions, prefix non-commit, and neural agreement.
`CommitPolicyRegressionTest` provides a readable table of known policy
outcomes. `WordSegmentationTest` correctly covers a unique split, missing
bigram, ambiguity, joined-word immunity, non-letter rejection, and casing.
`AutocorrectBehaviorRegressionTest` protects the intended semantic separation
between protected vocabulary, anti-correction pairs, contraction rules, and
soft contextual arithmetic.

**Agent inference:** These tests are valuable unit tests. Their failure was not
that they asserted nothing; their failure was that they were treated as proof
of provider-level behavioral preservation.

### Why they gave false confidence

- **Confirmed from source:** Policy tests manually supply
  `typedIsValidWord`, `isEditDistanceCandidate`, `isBlockedCorrection`, and
  `typedIsProtectedVocab`. They do not test whether runtime retrieval, assets,
  and orchestration derive those facts correctly.
- **Confirmed from source:** Numeric fixtures are one-sided negatives. They
  deliberately codify that every changed digit-bearing token is blocked and
  contain no positive prose-shaped digit substitution.
- **Confirmed from source:** No asset-backed test retrieves and ranks the real
  candidate set for `las`, `La's`, `L's`, `last`, and `law`.
- **Confirmed from source:** Apostrophe tests verify arithmetic and shortcut
  maps, but not whether a large apostrophe bonus is licensed by a legitimate
  contraction relationship.
- **Confirmed from source:** The `zsh` regression fixture manually marks
  `typedIsProtectedVocab = true`, but the real asset path protects `zsh` through
  dictionary exact-match evidence and valid-word immunity. The test simulates
  the wrong mechanism.
- **Confirmed from source:** Segmentation tests accurately test the designed
  exact-split algorithm; they do not and should not imply support for a split
  plus an internal typo.
- **Confirmed from source:** There is no primary/fallback parity table assembled
  from the evidence each path truly possesses.
- **Confirmed from source:** There is no provider-level assertion over final
  output order and `isEligibleForAutoCommit`, and no on-device integration
  assertion exposing engine mode or initialization state.

## 9. Architectural implications

**Agent inference:** The six-commit direction is broadly salvageable. The
regression does not justify discarding the separation between retrieval,
ranking evidence, policy, contraction knowledge, segmentation, and casing.
Instead, it shows that extraction boundaries require assembled-pipeline tests
and that shared policy must receive honest, equivalent evidence from every
caller.

- **Agent inference:** Token shape should be derived from the typed token alone:
  ordinary alphabetic, number, decimal, version-like, identifier-like, hash/code,
  or mixed alphanumeric.
- **Agent inference:** Candidate relation should separately describe how a
  candidate differs: exact, casing-only, edit substitution, transposition,
  deletion/insertion, prefix-only completion, segmentation, or other.
- **Agent inference:** Candidate provenance should state where it came from:
  packaged dictionary edit retrieval, prefix retrieval, user dictionary,
  contraction rule, segmentation, or fallback.
- **Agent inference:** Contraction-sized apostrophe evidence must be explicitly
  licensed by `ContractionRules` or another named morphology source. Merely
  containing an apostrophe in the dictionary is insufficient.
- **Agent inference:** General dictionary membership is useful evidence, not
  automatic proof that the user intended the typed form. Trust decisions need
  provenance and possibly admission quality, not only a boolean.
- **Agent inference:** Fallback must not fabricate evidence it does not possess.
  In particular, labeling all results edit candidates or applying primary
  immunity from a coarse membership check can create accidental conservatism.
- **Agent inference:** Commit authority should be centralized without bypasses.
  The current contraction fast path is a confirmed bypass of general
  `CommitPolicy` and neural evaluation, even though it performs its own
  protected and anti-correction checks.
- **Agent inference:** Repairing these distinctions should not be implemented by
  globally lowering thresholds, making correction universally aggressive, or
  adding exceptions for the reported words.

## 12. Handover summary

**Confirmed from source and repository data:** The primary deterministic replay
is equal between Phase 2 baseline `2dc236c8` and cleanup HEAD `55cd2cbf` for all
requested probes. The word-shaped digit failures come from an overbroad policy
guard already in the baseline. The `las` ordering comes from generic,

**Unresolved:** The investigation did not prove which path ran on the phone.

**Plausible but unproven:** The keyboard may have felt globally timid because
the disturbed installation left the n-gram engine unavailable and routed input

a conclusion.

**Agent inference:** The six commits should not simply be discarded. Most are
responsibility-preserving extractions that expose where the older assumptions
